Prior-art survey · open-source library concept

The Editable Mirror

Point a library at your website and get a Figma-grade editable mirror at a URL path — drag, align, retype — with every change written back to the real source code deterministically, no AI in the loop. This report surveys who has tried, what actually works, and which parts you can take.

Research date 2026-09-01 3 parallel research tracks · ~60 projects examined GitHub/npm stats verified live unless flagged

The verdict up front

The niche is real and open. Every deterministic visual-edit system that exists today either owns the whole dev environment (Onlook, Utopia, Codux) or is locked inside a hosted AI builder (Lovable, v0, Replit, Bolt). Nothing ships as "npm install, mount an editable mirror at /edit, point it at your already-running app." That exact quadrant — embeddable, deterministic, bring-your-own-dev-server — is empty, and 2025–26 market behavior (every major AI builder shipping a deterministic "visual edits" fast path; users revolting when v0 put simple edits back behind AI credits) says demand is proven.

The pipeline is also proven. Onlook, Lovable, and Codux independently converged on the same architecture: stamp stable IDs onto JSX at build time → resolve the clicked DOM node to a source span → apply a typed AST mutation → reprint with the project's own Prettier → let HMR close the loop. You would not be inventing the mechanism, you would be unbundling it into a library. One hard platform fact shapes everything: React 19 deleted _debugSource, killing all runtime DOM→source inspection — build-time instrumentation is now the only durable substrate.

01

The landscape: who has tried this

Roughly sixty projects fall into four camps. Only the first camp writes back to real source code. The others own the data model, and their source code is an export artifact — a fundamentally different product, however similar the canvas looks.

Camp 1 — visual edits that land in your actual source

OnlookApache-2.0ACTIVE · 26.6k ★

The closest existing thing to the idea — an open-source "Cursor for designers": a Figma-like canvas over a real React + Tailwind app with deterministic write-back (AI chat is a separate, additional path). Verified from source: a Babel pass (packages/parser) injects a persistent data-oid attribute into every JSX element in your files; an index maps oid → (file, AST span). Each edit type has its own deterministic writer module — style.ts (Tailwind merge), text.ts, insert/remove/move/group/layout/image — then Prettier normalizes. Edits are two-track: instant optimistic DOM mutation in the iframe, plus the same change as an AST patch that HMR confirms. Its in-frame agent exposes a ~40-method postMessage RPC (via Penpal) that is effectively a published spec of what an editing agent must do.

Where it falls short of the idea It owns the whole environment — your code loads into its CodeSandbox-based cloud container; you cannot point it at an existing running site. React/Next + Tailwind only. It persists data-oid noise into your repo. It is a hosted product, not an embeddable library.

Lovable "Visual Edits"PROPRIETARYACTIVE

The best published blueprint of the exact write-back pipeline (engineering post). A custom Vite plugin (lovable-tagger, visible on npm) assigns stable per-element IDs at compile time. The whole project syncs into the browser as a Babel/SWC AST. Simple edits — text, color, spacing, Tailwind classes — are declarative client-side AST mutations applied optimistically to the DOM, with a client-side Tailwind generator reading the project's config so new classes render before saving. Explicitly deterministic ("not AI") and explicitly anti-regex. Complex structural edits escalate to the agent.

Lesson The hybrid is the shipped consensus: deterministic fast path for property-level edits, AI escape hatch for structure. Locked inside their hosted builder — the mechanism is free to copy, the product is not reusable.

v0 Design Mode · Replit Visual Editor · BoltPROPRIETARYACTIVE

The 2025–26 convergence: every major AI app builder shipped a visual-edit mode. v0's Design Mode applies typography/color/spacing edits without AI or credits, snaps values to the project's Tailwind scale, understands shadcn/ui, and serializes each session into a normal reviewable diff. Its sharpest UX idea: selecting an element co-highlights every element rendered from the same code and edits them together — the honest answer to one-source-many-instances. Replit's docs likewise confirm simple edits "update the source code directly without consuming AI credits." Bolt's inspector, by contrast, only feeds selection context to the LLM.

Market signal When a v0 redesign put simple edits back behind AI credits, users revolted publicly. People specifically want the deterministic, free, instant path — the premise of this library.

UtopiaMITDEAD · 3.8k ★

The maximalist attempt: a browser IDE where the canvas runs the actual React app (parsed, transpiled, evaluated in-browser), with a formatting-preserving parser-printer giving full two-way sync between canvas and code, and VS Code embedded. Design values worth adopting verbatim: "whatever Utopia doesn't understand, it leaves as-is" and "allergic reactions to unnecessary code changes." Effectively dead since late 2024; utopia.app now serves a contact form.

Mineable Its parser-printer test suites (parser-printer-code-preservation.spec.ts and friends) are a ready-made spec of JSX round-trip edge cases — comments, conditionals, arbitrary expressions, UID stability. MIT, free to mine. Also a warning: owning a whole in-browser toolchain is enormous.

Codux (Wix)CLOSEDDISCONTINUED

Wix's desktop visual IDE for React: real project files, git, two-way sync through a typed "ASTModification" API over the TypeScript AST. Notably, their compile transformers mapped each React Fiber to the syntax node that created it — including which expression, loop, or condition — i.e. they instrumented expressions, not just elements, to explain rendered output from mapped lists and conditionals. Discontinued; codux.com now redirects to Dazl, an AI generation product.

Lesson Commercial validation of AST-modification write-back — and a second successor (after Tempo's pivot) abandoning the deterministic lane for AI generation, leaving it emptier.

Smaller and adjacent entries

  • Impulse MIT DEAD 2023 — the lightest-weight variant ever shipped: an in-browser editor injected into your dev app that toggled Tailwind classes and wrote JSX files directly via the browser File System Access API. No server, no SaaS, deterministic. 458 stars, abandoned — but the architecture sketch is exactly "library-weight."
  • stagewise AGPL-3.0 ACTIVE · 6.8k ★ — proved the injection UX the mirror wants: npx stagewise proxies your running dev server and injects a toolbar into the proxied page, zero app changes. But its write path is prompting AI agents, not deterministic edits, and it has since pivoted to a full agentic IDE.
  • Tempo Labs PIVOTED — YC-funded "Figma-like editor for real React code," pivoted to an agent factory in 2025. Another vacancy in the lane.
  • Pinegrow PROPRIETARY ACTIVE — long-lived desktop app that opens and saves plain HTML/CSS files directly, with a Tailwind visual editor add-on. Proof that deterministic file-level visual editing sells; not component-aware.
  • Figma Make, local-codebase beta (2026) — connect your repo, select elements in the live app, an agent edits code locally. Same thesis, agent-mediated, top-of-market demand proof.

Camp 3 — embeddable editor shells (JSON out, no source)

  • Puck MIT ACTIVE · 13.2k ★ — best-in-class embeddable React editor: registered components with typed fields, drag/drop with slots, inline text editing, overlay portals, same-origin iframe preview with host-style syncing. Emits a JSON data payload you persist. The editor shell is plausibly reusable as the mirror's UI layer.
  • GrapesJS BSD-3 ACTIVE · 26.2k ★ — the largest OSS builder framework, and the only one that ingests arbitrary existing HTML (lossily, into its own component model; export replaces source). Proof that point-at-existing-markup ingestion is tractable at the DOM level.
  • Craft.js MIT DORMANT · 8.7k ★ — headless editor-state engine; its query/actions API (setProp, add, move, undo history) is a clean reference for a deterministic edit-operation log — exactly the shape a code writer wants to consume.

Camp 4 — the mass-market proof: WordPress Gutenberg

Deterministic visual→text round-trip already runs ~41% of the web

Gutenberg serializes visual edits into HTML comments with inline JSON attributes (<!-- wp:image {...} -->…<!-- /wp:image -->), parsed back by a formal grammar. Three of its rules transfer directly: (a) each attribute lives in exactly one place — either the JSON or "sourced" from the markup itself, never duplicated; (b) on load, the editor re-runs each block's pure save() and validates it against the stored markup, surfacing mismatches as recoverable "invalid blocks" instead of silently clobbering hand edits — the proven pattern for coexisting with humans editing the same artifact; (c) a spec'd grammar keeps parsing testable. Determinism came from owning the file format; a JSX editor can't own the format, but can adopt all three disciplines.

02

Mapping a DOM node back to source

The whole idea stands or falls on one primitive: click a rendered element, get the exact source span that produced it. The history here has a hard break in it.

The React 19 extinction event

For years, every click-to-source tool free-rode on one mechanism: Babel's dev transform injected __source={fileName, lineNumber, columnNumber} into every JSX element, and React exposed it as fiber._debugSource. React PR #28265 removed it in React 19 (with findFiberByHostInstance), and 19.2's jsxDEV no longer receives source at all. This broke LocatorJS's runtime mode, click-to-component, react-dev-inspector, code-inspector's fiber path — the issues (#31981, #32574) remain open with no blessed replacement. The official direction, Owner Stacks (captureOwnerStack()), identifies the component usage chain via error-stack symbolication — not the clicked element's JSX callsite — and the community verdict is "hacky or fragile."

Design consequence

Never depend on framework internals. Everything still working in 2026 — Onlook, Lovable, code-inspector-plugin, LocatorJS's plugin mode — stamps elements at compile time. A bundler plugin you control is the only durable substrate, and it conveniently bounds "any website" to "any site whose build you can instrument," which is what every working system quietly accepts.

Persistent vs ephemeral IDs — the unresolved trade-off

Onlook persists IDs into source: stable across sessions and edits, ugly in the repo. Lovable and code-inspector stamp only the build output: clean repo, but file:line drifts the moment you write an edit back, so IDs must be recomputed after every write. A promising best-of-both (not shipped anywhere yet): ephemeral IDs whose build-time manifest stores byte offsets per element — enabling surgical magic-string writes — recomputed per build, with stale IDs treated as fatal.

The cleverest trick in the field: stega

Sanity's visual editing (MIT, active) pairs Content Source Maps (JSON mapping each query-result field to its document path) with stega: the client appends the mapping, encoded as invisible zero-width unicode (a base-4 alphabet of U+200B/C/D and U+FEFF), inside every rendered string. An overlay then scans DOM text nodes, decodes, and draws click-to-edit affordances — mapping that survives any DOM transformation because it travels inside the content. The encoder is @vercel/stega (MPL-2.0); Vercel and Netlify visual editing build on the same pattern. Known hazards are documented: broken string comparisons, corrupted slugs/URLs, payload bloat.

Transferable idea: stega-encode file:line into rendered strings and you get zero-build-integration mapping for text nodes — a complement to attribute stamping, covering only text but requiring nothing from the bundler.

A browser-blessed convention you can ride

Chrome DevTools' Automatic Workspace Folders (default since M-136) has dev pages advertise their source root at /.well-known/appspecific/com.chrome.devtools.json; Vite, Angular CLI, and Astro already serve it. A mirror library can consume the same endpoint to discover the project root with zero configuration. Meanwhile Chrome Workspaces itself marks the outer boundary of browser-native write-back: CSS edits persist to mapped files (even through Sass source maps), but DOM/Elements-panel changes explicitly do not, and CSSOM-created rules (CSS-in-JS) have no text source to save to. Chrome drew the line at "edit the authoring representation or don't persist" — this library's entire value is crossing that line via the AST instead.

03

Writing code back deterministically

"Deterministic" has a formal name: this is a bidirectional lens, and the shipped systems all work because they restrict themselves to lenses that are trivially well-behaved — editing literals, class strings, and child order. Nobody attempts general program inversion, and neither should this library.

The toolchain (all MIT, all alive)

LibraryLast publishRole in the pipeline
recast2026-08Lossless reprint: keeps a shadow copy of the original source and reprints only mutated subtrees, preserving quotes, indentation, and comments elsewhere — minimal diffs, review-friendly
magic-string2026-08Surgical string edits by byte offset, zero reformat risk — the strongest option if the annotation manifest records exact ranges
jscodeshift2026-07Codemod runner over recast; batch transforms
ts-morph2026-04Type-aware TS manipulation — e.g. answering "does this component forward className?"
tailwind-merge2026-05Deterministic class conflict resolution: classes bucketed per CSS property, variant-aware, last-wins — the semantics every Tailwind writer leans on

The Prettier recipe, per Prettier's own guidance: never codemod through Prettier's parser API. Edit via AST or string, then run the project's own Prettier version and config on the changed file — a later format-on-save is then a no-op. Onlook vendors a prettier step for exactly this.

How the two shipped systems actually write

  • Onlook (verified in source): plain Babel parse, mutate, then generate(ast, {retainLines: true}) — a full-file reprint with line retention, normalized by Prettier. They accepted losing byte-exact formatting. Tailwind edits: if className is a string literal → merge via their tailwind-merge wrapper; if it's a cn(...)/clsx(...) call → push a new string-literal argument; else insert the attribute. Known gap: template-literal classNames. Layout drags are written as flex/grid utility classes, not inline styles. Moves are tracked with sentinel key prefixes.
  • Lovable: the same vocabulary, executed client-side against the synced AST, with a client-side Tailwind JIT reading the project config so unsaved edits render instantly. Save → write file → HMR.

Why every writer targets Tailwind

A className string is a single deterministic write target: one attribute per element, value→class is (mostly) a pure function, conflict resolution is delegated to tailwind-merge semantics, and arbitrary values (w-[137px]) guarantee any drag result is expressible. Writing to CSS files instead reintroduces the genuinely hard problems — selector→element mapping is many-to-many, plus specificity and cascade reasoning — which is why nobody deterministic does it except Chrome-with-sourcemaps. The design tension to own: snap to the project's theme scale first, fall back to arbitrary values only when needed (v0 already does this). Conveniently, the target audience — AI-generated frontends — is overwhelmingly React + Tailwind.

The theory, for load-bearing confidence

The academic frame is bidirectional lenses (Foster/Pierce): a get/put pair obeying round-trip laws — precisely the guarantee "this visual edit maps to exactly one code edit, and re-rendering reproduces what you saw." Sketch-n-Sketch (Chugh et al., UChicago) is the deep exploration: it runs programs in reverse, tracing rendered values to source literals and inverting constant computations ("output-directed programming"). Its transferable core: literal provenance is the tractable deterministic kernel; everything else is ambiguous and needs policy. The shipped products are, in effect, Sketch-n-Sketch restricted to the kernel — which is exactly why they work.

04

The mirror & the editing feel

Two more subsystems make or break the product: how the editable mirror hosts the real page, and whether manipulating it feels like Figma. Both have rich prior art — and one surprising dead zone.

Hosting the page: the architecture menu

  • Iframe + cooperating in-frame agent over typed postMessage RPC — what every serious editor uses (Onlook, Plasmic, Builder, all the CMS bridges). Two protocols worth copying wholesale: Onlook's ~40-method preload API (getElementAtLoc, updateStyle, startDrag, editText, captureScreenshot…) and Sanity's @sanity/comlink handshake (state machine, heartbeats, origin validation).
  • Dev-server middleware mounting the editor at a path — a Vite/Next plugin serving the editor at /__mirror, iframing the app same-origin. Same-origin by construction kills the entire cross-origin pain list: X-Frame-Options, CSP frame-ancestors, cookie partitioning, postMessage origin dances. And the plugin is the same place the ID-stamping transform lives. This is the least-served quadrant in the whole survey.
  • CLI proxy (npx mirror à la stagewise) — proxy the running dev server, inject the agent script, for projects you can't add a plugin to. stagewise proved the UX then pivoted away.
  • Full rewriting proxies for arbitrary sites — Ultraviolet, Scramjet (Rust/WASM JS rewriter on OXC, emits source maps), and Webrecorder's wombat are existence proofs that same-origin mirroring of any site is possible, and equally proof of the cost: CSP stripping, client-side cookie jars, neutralizing the target's own service worker, WebSocket tunneling. All the good code is AGPL. And Hypothesis Via is the decade-long cautionary tale — they shut their open proxy down because attackers used it to launder phishing URLs. Verdict: keep at most a thin localhost-only fallback; refuse third-party origins.
  • rrweb — the wrong mirror for editing (its replica is inert by design: no framework state, edits clobbered by the next mutation batch), but its Mirror id-map and syncit's tiny {action, id} reverse-control messages are the proven template if a second-pane/second-machine mirror mode is ever wanted.

Nobody has solved the one problem the mirror URL actually implies

Extensive search found no OSS project that mirrors a live Vite/Next dev server, with working HMR, under a URL path. HMR websocket URLs are built from location, native ESM resolves against location.origin, and dev servers assume they own the root. The dev-server-plugin architecture sidesteps the problem (same origin, same server); a proxy architecture hits it head-on. Decide this early — it is the deepest technical fork in the project.

The "feels really good" layer

The editing physics are a genuinely open flank. The feature-complete OSS implementation of Figma-style handles — moveable and the Scena ecosystem (snappable with element guidelines, equal-spacing gap snapping, distance labels, group transforms, warp) — has been dormant since December 2023 with ~450 open issues, while still serving ~611k weekly downloads. Nothing maintained replaced it; working smart-guide engines now live only inside editors.

  • Excalidraw's snapping engine (packages/excalidraw/snapping.ts, MIT) — the best modern reference: corner/center point snaps, equal-spacing gap snaps, an 8px threshold scaled by zoom, references from visible non-selected elements, per-drag caching.
  • interact.js (MIT, alive) — the cleanest published architecture: headless, events-not-mutations, with snapping/restriction/aspect as composable modifier pipelines. Events-not-mutations fits a source-writing editor perfectly — the editor decides whether a "move" becomes a transform, a flex-order change, or a code edit.
  • selecto — the standard marquee↔handles hand-off contract (press on selected → group drag; press on empty → marquee). VisBug (Apache-2.0) — per-tool module + hotkey architecture, dependency-free guides and measurement via getBoundingClientRect + 1px line elements, shadow-DOM-piercing hit testing.
  • Overlay chrome: never inside the app's DOM — a custom element or portal outside body (Sanity mounts <sanity-visual-editing> exactly there), geometry synced via gBCR + ResizeObserver + MutationObserver, IntersectionObserver gating (Sanity only attaches to ≥30%-visible elements). Floating UI's autoUpdate + virtual elements solve toolbar anchoring across the iframe boundary. Text editing: per-element contenteditable (prefer plaintext-only), commit on blur/Escape, beforeinput interception — never execCommand (deprecated), never whole-page designMode (no commit boundary; your own UI becomes editable).

A maintained, standalone smart-guides/snap engine would be valuable to the ecosystem independent of the mirror — a natural first extraction and adoption wedge.

05

Failure modes to design for

Each of these has a named precedent. Determinism means having an explicit policy for every one — including "refuse."

  • Mapped lists — N DOM nodes from one JSX callsite; a per-instance edit is inexpressible. Detect duplicate IDs and either edit all instances or refuse. v0's co-highlighting is the honest UI; Codux's expression-level instrumentation is the deep fix.
  • Dynamic classNames — template literals (Onlook's known bug), clsx(cond && …), prop-driven styles. The only safe move is appending a literal (Onlook pushes an argument into cn()); conditional branches are untouchable.
  • Third-party components — the annotator never saw their source; only the local usage site is editable, and whether className is forwarded is unknowable without type info (ts-morph can check).
  • Non-Tailwind styling — CSS files/modules/styled-components reintroduce selector→element ambiguity. Reasonable v1 scope: Tailwind + inline style + literal props, which matches the AI-generated-frontend audience.
  • Dynamic text — literal JSX text is safe; props/CMS/i18n text is not. Sanity's stega shows the deterministic answer for CMS text is a different pipeline (map to the content store, not the code).
  • Concurrent hand edits — the file changed between annotation and write. Re-parse and re-resolve IDs before every write; treat stale ephemeral IDs as fatal; adopt Gutenberg's validate-then-flag recovery rather than silent clobbering. Figma-style multiplayer on source is text-level CRDT territory (Yjs; Zed's buffers) — punt in v1.
  • Framework drift — never touch fibers (React 19 proved why). Happy corollary: the build-time architecture ports to Vue via sourcemap tracing and to Svelte via __svelte_meta essentially for free.
06

The gap, the blueprint, the parts bin

The open gap, precisely

  • Packaging. No embeddable open-source library exists — everything deterministic owns the dev environment or lives in a hosted builder. "npm install → editable mirror at a path on your own dev server" is unoccupied.
  • "Any website" ingestion. Only GrapesJS (lossy) and AI cloners touch it. Every working deterministic system requires instrumenting the build — honestly scoping the promise to "any site whose build you can instrument" is both necessary and sufficient for the target user.
  • Framework breadth. Every deterministic write-back system is React+Tailwind only. code-inspector-plugin proves the mapping layer generalizes; nobody has built write-back on top for Vue/Svelte/Solid.
  • Deterministic structural layout. The proven surface is text, classes, spacing, reorder. Drag-to-reflow for arbitrary code is where every competitor escalates to AI — the hard open problem and the sharpest differentiator if cracked (even partially, e.g. within flex/grid containers only).
  • Editing physics. The Scena/moveable void: no maintained standalone smart-guides engine since 2023.

The convergent blueprint

Assembled from what Onlook, Lovable, Codux, and the mapping tools independently converged on — no step is speculative:

Instrument at build

A Vite plugin (then webpack/turbopack via code-inspector's matrix) stamps every JSX host element with a stable ID → manifest of file + AST span (ideally byte offsets). Dev-only; repo stays clean. Discover the project root via com.chrome.devtools.json.

Mount the mirror same-origin

The same plugin serves the editor at /__mirror, iframing the app same-origin. An injected in-frame agent speaks a typed RPC (Onlook's preload API is the spec; comlink's handshake is the transport pattern). CLI-proxy fallback for uninstrumentable projects, localhost-only.

Figma-grade overlay

Selection chrome outside the app's DOM; marquee↔handles per selecto's contract; snapping from Excalidraw's math in an interact.js-style modifier pipeline; guides and measurements per VisBug; contenteditable="plaintext-only" for text.

Two-track edits

Every gesture applies instantly as an optimistic DOM mutation and is recorded as a typed operation (the Craft.js-shaped log): setClasses, setText, setProp, insert, remove, reorder. Undo/redo falls out of the log.

Deterministic write-back

Resolve ID → file + span; apply the operation via recast (minimal diffs) or magic-string (exact offsets); Tailwind values snap to the project scale, arbitrary values as fallback, conflicts via tailwind-merge semantics; run the project's own Prettier; HMR repaints the mirror and confirms the loop.

Validate, never clobber

Gutenberg's discipline: re-derive after every write, treat stale IDs as fatal, surface conflicts with recovery UI. Refusal with a reason ("this element comes from a list rendered at Card.tsx:12") is a feature, not a failure.

Positioning in one line

Onlook proved the mechanism inside a walled product; Lovable, v0, and Replit proved the demand inside theirs; React 19 forced everyone onto the build-time architecture this library would need anyway; and the embeddable, framework-spanning, bring-your-own-dev-server version — the library — is still nobody's.
